# AGENTS.md — для ИИ-агентов, разрабатывающих этот репозиторий

## Что это за проект

**knowledge-extraction** — agent-skill: извлечение знаний из внешних материалов
(статьи, YouTube, аудио/видео, PDF/DJVU/HTML) через [TasK API](https://docs.ai-aid.pro/redocly)
без загрузки всего материала в контекст агента. Workflow: `ingest → chat → search →`
сохранение результатов.

Документация по адресатам: `SKILL.md` — инструкции для агентов-пользователей,
`README.md` — для людей, этот файл — для разработки самого скилла.

Скилл устанавливается в рабочие проекты (симлинком или git-клоном). После мержа
в `main` синхронизируй установленные git-клоны (`git pull --ff-only`); симлинки
обновляются сами.

## Архитектура

```
scripts/
  common.sh   — общее: workspace-резолвер, конфиг, api_json (curl-обёртка), кеш
  ingest.sh   — загрузка источников (URL / файл / stdin-текст) + --check статусов
  chat.sh     — диалог с источниками через TasK Chat API (SSE)
  search.sh   — поиск по чанкам (Chunks API)
tests/        — офлайн-тесты на мок-HTTP-серверах (python3), прод не трогают
```

**Контракт вывода `ingest.sh`** (stdout, машиночитаемый, не ломать):
`project_uuid=`, `source_uuid=`, `documents=`, `url=`. Диагностика — в stderr
(`[INFO]`/`[WARN]`/`[ERROR]`).

**Конфиг `.task_project.json`** (в корне рабочего проекта пользователя):

```json
{
  "active": "<последний использованный проект>",
  "projects": {
    "<имя>": {
      "uuid": "…", "title": "…", "description": "…",
      "sources": {
        "<url или text:<название>": {
          "uuid": "…", "url": "…", "title": "", "status": "pending|processing|ready|failed",
          "last_used": "…", "kind": "source|result"
        }
      }
    }
  }
}
```

- `kind: source` — первоисточник, `kind: result` — результат ресёрча (текст через
  `--source-text`); в чат «по первоисточникам» результаты не включают.
- Формат менять только обратно-совместимо; старый одиночный формат (`{uuid, sources}`)
  мигрирует на месте в `state_migrate()`.

## Критичные детали TasK API

Эти знания добыты практикой — не «упрощай» их обратно:

- Статус источника — **`preparationStatus`** (в API v0.10.0 переименован из
  `status`; скрипты читают оба варианта).
- Список источников проекта пагинирован (`pagination.total` — стоп-условие),
  см. `all_sources()`.
- Создание источников: `POST /projects/{uuid}/source-urls` `{uri}` — по URL;
  `POST …/source-files` — multipart-файлы; `POST …/source-contents`
  `{content, documentName}` — текст (результаты ресёрча). Один и тот же URL для
  одного creator'а переиспользуется — API вернёт существующий sourceUuid.
- Чат: `POST /chats` `{projectUuid, title, sourcesUuids?}` →
  `POST /chats/{uuid}/messages` `{message}` — ответ приходит **SSE**-стримом;
  ошибки API приходят обычным JSON — нельзя скармливать их парсеру SSE.
- Исходящие HTTP-запросы ограничены таймаутами; недоступные/медленные сайты
  дают быстрый отказ (HTTP 422), а не зависание — при повторной загрузке того же
  URL API не дублирует источник.

## Разработка и тесты

- Зависимости: `bash`, `curl`, `jq`, GNU `realpath`; python3 — только для моков в тестах.
- Перед любым пушем: `bash -n scripts/*.sh tests/*.sh` и полный прогон `tests/*.sh`.
- Новый сценарий — новый офлайн-тест на мок-сервере (образцы: `tests/named-projects.sh`,
  `tests/result-compilation.sh`). CI гоняет только офлайн-тесты — прод из CI недоступен.
- `jq`-однострочники в скриптах должны быть null-safe (`// {}`, `// empty`) —
  конфиг пользователя содержит произвольные поля.
- Отладка против TasK — через тестовый проект и фиктивные данные; не гоняй
  реактовые материалы через API без нужды (обработка платная, особенно для видео).

## Правила работы с git

Прямые пуши в `main` запрещены. Порядок:

1. Ветка от актуального `main`: `task/<краткое-имя>`.
2. Локально перед пушем: полный прогон тестов, все зелёные.
   Коммитить непрогнанное нельзя.
3. `git push -u origin task/<краткое-имя>` → PR в `main` через `gh pr create`.
4. Дождаться зелёного CI (см. `.github/workflows/ci.yml`).
5. **Merge — только после явного подтверждения пользователя** («мержи», «принял»).
   Самовольно мержить нельзя, даже при зелёном CI: PR существует, чтобы
   пользователь посмотрел diff до попадания в `main`.
6. После мержа (squash): удалить ветку, синхронизировать локальный `main`
   и установленные git-клоны скилла.

Коммиты — короткие английские повелительные («Drop site-specific note…»).
Рабочий язык документации и диалога — русский.

## Секреты

`.task_token.json` никогда не коммитится, не читается и не пересоздаётся агентом —
его создаёт пользователь. Тесты используют фиктивные токены и мок-сервер на
`127.0.0.1`; никаких обращений к прод-API из CI и тестов.
