# Knowledge Extraction

## Как использовать

```text
ingest → chat   (поговорить с документом — приоритет)
       → search  (собрать чанки — запасной, если ответы чата кажутся странными)
       → результат ресёрча — сохранить обратно в проект
```

### Шаг 1: Загрузить материалы

```bash
# Загрузить один источник (ждёт готовности)
scripts/ingest.sh --source-url <URL>

# Загрузить локальный файл (multipart/form-data)
scripts/ingest.sh --source-file "/path/to/video.mp4"

# Проверить статусы всех источников (без ожидания)
scripts/ingest.sh --check
```

Опции:

| Опция | Обязательно | По умолчанию |
|---|---|---|
| `--source-url` | URL или файл (кроме `--check`) | — |
| `--source-file` | Нет | — |
| `--source-text` | Текст из stdin | — |
| `--title` | Для `--source-text` — да | «Результат ресёрча ⟨дата⟩» |
| `--list` | Нет | Метаданные всех источников |
| `--info --source <UUID>` | Нет | Карточка источника + состав документов |
| `--project-name` | Нет | Имя текущей папки |
| `--project-description` | Нет | «Материалы для извлечения знаний» |
| `--project` | Нет | Из `.knowledge-extraction.json` |
| `--diarization yes\|no\|auto` | Нет | Выкл — разметка спикеров в транскрипте (видео/аудио) |
| `--language auto\|en\|ru\|zh` | Нет | auto |
| `--include-comments true\|false` | Нет | true — false: комментарии не скачиваются и не индексируются |
| `--update --source <UUID>` | Нет | — — обновить параметры обработки готового источника |
| `--check` | Нет | — |

Создаёт проект (название — имя текущей папки или `--project-name`), загружает source, ждёт готовности. Повторный вызов с тем же URL не дублирует загрузку. Для локального файла последующий диалог запускай с `--source <UUID>` из вывода `ingest.sh`.

YouTube обрабатывается дольше — транскрибация через Whisper может занять минуты (для длинных видео — десятки минут). Агент может загрузить несколько источников, пока одни обрабатываются — работать с готовыми, а статус pending проверять через `--check`.

Результат: строки `project_uuid=...`, `source_uuid=...`, `documents=N`.

#### Типовые ситуации при загрузке

- **`documents=0`** — источник пустой: чат и поиск по нему ничего не вернут. Сайт мог не проиндексироваться. Не перезапускайте `ingest.sh` с тем же URL по кругу — проверьте доступность URL и попробуйте позже либо используйте другой источник.
- **Таймаут ожидания (~10 мин)** — источник остаётся в очереди на стороне API. НЕ вызывайте `ingest.sh` повторно с тем же URL — загрузка уже идёт. Работайте с другими источниками, статус проверяйте через `--check`.
- **Долгие видео** — транскрибация занимает десятки минут. Запускайте несколько источников параллельно, работайте с готовыми, отложенные проверяйте `--check`.
- **Проверяйте строку `Проект:` в выводе** — имя проекта берётся из текущей папки. Скрипты запускаются из корня рабочего проекта, а не из папки скилла: иначе источники попадут в чужой проект.
- **Некоторые сайты не индексируются** — это видно по ошибке загрузки или `documents=0`. Если материал критичен, скажите пользователю и прочитайте его напрямую — но только после того, как скилл не сработал, не вместо него.

### Шаг 2: Извлечь знания

**Через диалог (приоритет):**

```bash
# Новый диалог — вернёт chat_uuid=... первой строкой
scripts/chat.sh --source <UUID>

# Или с несколькими источниками
scripts/chat.sh --source <UUID1> --source <UUID2>

# Или без источников — используются все source'ы проекта
scripts/chat.sh

# Продолжить диалог — указать chat_uuid из вывода предыдущего вызова
scripts/chat.sh --chat <UUID> --question "..."
```

Опции:

| Опция | Обязательно | По умолчанию |
|---|---|---|
| `--source` | Нет | Все source'ы проекта |
| `--source-url` | Нет | — (разрешается в `--source` из кеша) |
| `--chat` | Для продолжения | — |
| `--question` | Для продолжения — да | «О чём этот материал?» |
| `--title` | Нет | Заголовок первого source или «Диалог с материалом» |
| `--exclude-comments` | Нет | Комментарии включены — флаг исключает их из контекста чата |
| `--project-name` | Нет | Последний использованный в каталоге |
| `--project` | Нет | Из `.knowledge-extraction.json` |

Если вопрос относится ко всему набору материалов, не передавай `--source`: чат
использует все sources проекта и сам подберёт релевантные фрагменты.

**Разные ресёрчи — разные проекты.** Один вопрос или одна тема — один проект:
передавай `--project-name <имя-ресёрча>` во все вызовы (`ingest.sh`, `chat.sh`,
`search.sh`) — в рамках одного рабочего каталога каждый ресёрч получит свой проект
TasK и свой набор источников в `.knowledge-extraction.json`. При создании проекта давай
осмысленное `--project-description "…"` — назначение сохраняется в конфиге рядом
с UUID, и по нему в следующих сессиях видно, какой проект для чего. Без
`--project-name` всё складывается в общий проект каталога — тогда чат «по всем
источникам» смешает несвязанные материалы и точность ответов упадёт.

Агент ведёт диалог, а не кидает все вопросы разом:

1. `scripts/chat.sh --source-url ... --title "Дороничев — прыжок веры"` — первый вопрос с осмысленным именем чата
2. Читает ответ, видит пробелы или интересные нити
3. `scripts/chat.sh --chat <UUID> --question "..."` — уточняющий вопрос в том же чате
4. Повторяет, пока не извлечёт нужное

**Не создавай новый чат без необходимости.** Если диалог уже начат — продолжай его через `--chat <UUID>`. Новый чат — только для нового материала или новой темы.

Пример стратегии диалога (рекомендация агенту):

1. «О чём этот материал?»
2. Взять title и description источника из API, спросить: «Какие темы раскрывает автор под заголовком „…"? Приведи утверждения из текста.»
3. По ответу найти пробелы: «Ты упомянул X, но не раскрыл Y. Что говорит автор про Y?»

**Правило атомарных вопросов (соблюдай строго).** RAG ищет чанки по тексту
сообщения: один вызов `chat.sh` — один поиск. Составной вопрос из нескольких
тем размывает поиск: релевантные чанки находятся не под все темы, и модель
отвечает на «хвосты» по памяти — пересказом вместо цитат. Несколько простых
вопросов всегда лучше одного сложного.

**Задавай вопросы строго последовательно:** задал вопрос → прочитал ответ →
следующий вопрос. Ответ на предыдущий показывает, нужен ли следующий и как
его уточнить. Не отправляй несколько `chat.sh` параллельно за один ход.

Плохо (простыня из четырёх вопросов — под «хвосты» чанки не найдутся):
> «Как материалы описывают разделение ролей между людьми и ИИ: специализация,
> диспетчеризация, ревью, верификация, governance? Какие новые роли и структуры
> команд появляются? Можно ли команду с агентами назвать мультиагентной
> системой? Приведи формулировки.»

Хорошо (те же темы — цепочкой, каждая после ответа на предыдущую):
> 1. «Как материалы описывают разделение ролей между людьми и ИИ-агентами? Приведи формулировки.»
> 2. — прочитал ответ → «Какие новые роли и структуры команд упоминаются?»
> 3. — прочитал ответ → «Есть ли сравнение команды с агентами с мультиагентной системой?»

**Самопроверка перед отправкой** — разбивай вопрос, если в нём:
- больше одного знака «?»;
- союзы «и», «а также», «заодно», склеивающие разные темы;
- после двоеточия перечислены разные темы.

Перечисление **синонимов одной темы** допустимо и полезно — поиск найдёт чанки
под любой из вариантов: «роль менеджера, диспетчера, верификатора». Перечисление
**разных тем** — это несколько отдельных вопросов.

**Глубина проработки.** Один-два вопроса на источник дают конспект, не
исследование. Если задача — статья, сравнение позиций или проверка утверждений,
прогони источник через несколько проходов; каждый следующий строй по ответам
на предыдущий:

1. **Обзор**: «О чём материал? Какие темы раскрывает?»
2. **Методология и ограничения**: что автор сам признаёт ограничением? Что
   подаёт как гипотезу, а что как доказанное? Откуда цифры и параметры — замеры
   или заданы вручную? На каких данных проверялось и где выводы могут не
   масштабироваться?
3. **Темы по одной** — атомарными вопросами, с требованием формулировок.
4. **Верификация ключевых тезисов**: каждую цифру и сильное утверждение проверь
   отдельным вопросом: точная формулировка? откуда данные — исследование, опрос
   или собственная прикидка автора («на моих мероприятиях так вышло»)? какими
   оговорками он её сопровождает? Прикидка эксперта — не данные исследования,
   реплики зрителей в комментариях — не слова автора. Транскрипты интервью,
   подкастов и панелей не размечены по спикерам: «кто сказал» — гипотеза из
   текстовых подсказок («он сказал такую вещь», «я вхожу в…»). Пересказ чужих
   слов приписывай тому, в чьём пересказе записана цитата, а не тому, кого
   пересказывают. Личность спикера считай установленной, только если он
   представился в тексте; иначе атрибутируй запись («в докладе X»), а не
   человека.
5. **Противоречия между источниками**: не задавай сводный вопрос «сравни позиции
   A, B и C» чату с тремя источниками — RAG отберёт чанки преимущественно одного
   из них, сравнение не состоится, а цитаты останутся без атрибуции. Спроси
   каждый источник отдельно (чат по всем источникам — только для широких
   вопросов вроде «о чём это?»), сопоставь ответы сам, а спорную цитату
   атрибутируй точечным вопросом конкретному источнику.
6. **Слепые зоны и конфликты интересов**: чей это продукт или компания? Есть ли
   независимые оценки помимо маркетинга автора?
7. **Иерархия утверждений** в выводах: данные исследования / эксперимент /
   мнение или прикидка автора / маркетинг. Пересказ чужих слов («мне рассказали,
   что…») помечай как пересказ — это не позиция самого автора.

**Состав источника: документы.** Видео-источник — это обычно два документа:
транскрипт (`type: main`) и комментарии зрителей (`type: comments`) — последние
могут занимать до половины объёма. Состав смотри в `ingest.sh --info --source <UUID>`
(поле `documents`), он же печатается в stderr при загрузке. Управляй составом
на трёх уровнях:

- **При загрузке**: `--include-comments false` — комментарии вообще не скачиваются
  и не индексируются. Если это интервью/лекция/подкаст — добавляй `--diarization auto`:
  в транскрипте появится разметка спикеров.
- **В чате**: `chat.sh --exclude-comments` — диалог без комментариев; работает и для
  источников, загруженных раньше с комментариями (новые чаты — параметр создания,
  существующие — PATCH перед вопросом).
- **В поиске**: `search.sh --exclude-comments` — фильтр `documentTypes: ["main"]` на
  сервере: лимит выборки не тратится на комментарии.

Цитаты из документа «Комментарии к …» — реплики зрителей, не слова автора. Комментарии
сами по себе могут быть ценным материалом (реакция аудитории, возражения) — отключай их
только когда нужны именно слова автора.

**Атрибуция с диаризацией.** Диаризация даёт анонимные метки в тексте чанков
(`Speaker 00:`, `Speaker 01:` — у каждого источника нумерация своя). Маппинг «кто
есть кто» строй только по чанку с самопрезентацией, найденному поиском:
`search.sh --query "меня зовут ведущий гость представляется"` — в выдаче метка стоит
рядом с фразой «Я Алексей Семихатов», и это авторитетное соответствие. Слепой вопрос
чату «кто такой Speaker 00?» ненадёжен: если чанк с самопрезентацией не попал в
контекст, модель может перепутать метки местами и не заметить этого. Помни: сущности
с именем спикера в чанках нет — вопросы «что сказал Ключарёв» находятся по содержанию,
а не по имени.

Найденный маппинг сохраняй для переиспользования:

```bash
scripts/speakers.sh --source <UUID> set --json '{"Speaker 00": {"name": "Анохин Константин", "role": "гость", "evidence": "Во-первых, я не очень много изучал сознание…"}, "Speaker 01": {"name": "Семихатов Алексей", "role": "ведущий", "evidence": "Я Алексей Семихатов, здравствуйте"}}'
```

Маппинг хранится в кеше проекта (попадает в `--info`, поле `speakers`). Перед новым
диалогом по источнику проверь `speakers.sh --source <UUID> get` — если маппинг уже
есть, используй его, не переопределяй. После `--update` метки могут смениться —
перепроверь маппинг по самопрезентациям и пересохрани. Если спикеры не представились —
атрибутируй по ролям («ведущий», «гость») и скажи пользователю, что имена не названы.

**Старые источники**: чтобы включить диаризацию или убрать комментарии у уже загруженного
источника — `ingest.sh --update --source <UUID> --diarization auto --include-comments false`.
Для видео это повторная платная транскрибация — запускай осознанно.

**Через чанки (запасной):**

```bash
# Один запрос — один вызов
scripts/search.sh --source <UUID> --query "запрос"

# Прочитал результат, видишь пробел — следующий запрос
scripts/search.sh --source <UUID> --query "уточняющий запрос"

# Только транскрипт, без комментариев зрителей
scripts/search.sh --source <UUID> --query "запрос" --exclude-comments
```

Опции:

| Опция | Обязательно | По умолчанию |
|---|---|---|
| `--source` | Нет | Из `.knowledge-extraction.json` по `--source-url` |
| `--source-url` | Нет | — (разрешается в `--source` из кеша) |
| `--project-name` | Нет | Последний использованный в каталоге |
| `--project` | Нет | Из `.knowledge-extraction.json` |
| `--query` | Да | — |
| `--exclude-comments` | Нет | Серверный фильтр `documentTypes: ["main"]` + клиентский фолбэк |

Агент ведёт поиск итеративно, как диалог:

1. `scripts/search.sh --query "основной тезис"` — первый запрос
2. Читает чанки, видит пробелы
3. `scripts/search.sh --query "уточнение по теме X"` — следующий запрос
4. Повторяет, пока не соберёт достаточно фактов

### Шаг 3: Сохранить результаты ресёрча

Выводы, саммари и зафиксированные тезисы складывай обратно в проект — в следующих
сессиях они станут частью контекста, и по ним можно будет спрашивать тем же чатом:

```bash
chat.sh --project-name sdd-research --question "…"   # получил ответ
printf '%s' "## Выводы\n- …" | \
  ingest.sh --project-name sdd-research --source-text --title "Выводы: SDD-ресёрч"
```

Текст из stdin сохраняется с меткой `kind: result` в `.knowledge-extraction.json` —
первоисточники помечены `kind: source`. По метке различай два типа записей:

- **Первоисточники** — слова автора. Цитаты и факты бери из их чанков.
- **Результаты ресёрча** — твои своды. Отвечают на вопрос «что мы уже выяснили»,
  а не «что говорит автор».

Чат создаётся с набором источников — включай в него то, что нужно для задачи:
когда нужны слова автора, передавай первоисточники явно через `--source` /
`--source-url` и не включай результаты. Поиск по результату покажет пометку
«результат ресёрча (не первоисточник)».

Каждый результат — под осмысленным `--title` (по умолчанию «Результат ресёрча
⟨дата⟩»); повтор с тем же названием пропускается, новая версия — под новым.

### Шаг 4: Оформить результат

Агент оформляет извлечённые знания под задачу:

- **Саммари** — суть + ключевые тезисы с цитатами
- **Факты** — утверждения автора с подтверждающими фрагментами
- **Рекомендации** — выводы и практические следствия из материала

Соблюдай достоверность:

- Отделяй утверждения автора от собственных выводов.
- Не выдавай пересказ за точную цитату.
- Для точной цитаты найди исходный чанк через `search.sh` и сверь формулировку.
- Ссылайся на исходный URL или имя локального файла.
- Если материал не подтверждает ответ или источники противоречат друг другу, скажи об этом явно.

### Примеры

**Полный цикл извлечения:**

```bash
# 1. Загрузить
scripts/ingest.sh --source-url "https://habr.com/ru/articles/1061876/"

# 2. Начать диалог (вернёт chat_uuid=...)
scripts/chat.sh --source-url "https://habr.com/ru/articles/1061876/"

# 3. Уточнить
scripts/chat.sh --chat <UUID> --question "Какие 4 убеждения разбирает автор?"

# 4. Оформить подтверждённый материалом ответ
```

**Диалог:**

```bash
scripts/ingest.sh --source-url "https://habr.com/ru/articles/1061876/"
scripts/chat.sh --source-url "https://habr.com/ru/articles/1061876/"
# → читаем ответ, задаём уточняющие вопросы через --chat <UUID>
```

**Поиск чанков (запасной режим):**

```bash
scripts/search.sh --source-url "https://habr.com/ru/articles/1061876/" \
  --query "теория локуса контроля Роттера"

# → читаем чанки, видим что не раскрыта тема таланта
scripts/search.sh --source-url "https://habr.com/ru/articles/1061876/" \
  --query "талант врождённый или приобретённый"
```

## Результат

**`ingest.sh`** — строки `project_uuid`, `source_uuid`, `documents` в stdout.

**`chat.sh`** — ответы TasK на каждый вопрос в markdown.

**`search.sh`** — чанки с номерами, документом и текстом в markdown.

## Локальные файлы

Один файл на уровне рабочего проекта — `.knowledge-extraction.json`. Хранит именованные
проекты: UUID, маппинг URL → source UUID и статус каждого источника (`pending` /
`processing` / `ready` / `failed`). Создаётся автоматически при первом запуске
`ingest.sh`.

Статусы обновляются:
- При загрузке — `ingest.sh` сохраняет актуальный статус после ожидания
- Без ожидания — `ingest.sh --check` сверяет кеш с API и показывает изменения

```bash
$ scripts/ingest.sh --check
youtube.com/watch?v=... → processing ✦
github.com/.../wsff.md → ready
Изменений: 1
```

`--check` получает все страницы sources из API и добавляет в cache источники, созданные в другой сессии. Записи сопоставляются по UUID: пользовательские поля cache не стираются, а sources с одинаковым URL, но разными UUID сохраняются отдельно.

Ошибки API не маскируются: `chat.sh` пишет безопасную диагностику в stderr, например `HTTP 422: Need to top up balance.`, и не пытается разобрать такой ответ как SSE.
